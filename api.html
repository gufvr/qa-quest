Pergunta do teste: estas respostas atendem ao contrato que seus consumidores esperam?

Quatro cenários e cinco respostas simuladas. Cada fixture é um conjunto fixo de dados de teste. No catálogo, compare a referência do contrato com a fixture da candidata. No checkout, API-02 e API-03 usam o mesmo método, rota e body, com respostas didáticas independentes: uma aderente e outra com falhas. Repetir uma fixture produz o mesmo resultado. Todos os dados são preparados localmente; não são capturas de duas chamadas reais à candidata BZ-2026.12.0.

Glossário e relação com as outras missões

API: uma forma de sistemas trocarem pedidos e respostas. Aqui, cada resposta é uma representação didática definida no navegador.

Método: operação, como GET para consultar ou POST para enviar dados e criar o pedido previsto neste contrato. Rota: caminho do recurso, como /api/catalog.

Parâmetro de consulta: filtro após “?”, como category=accessories. Parâmetro de rota: identificador no caminho, como BZ-API-1042 em /api/orders/BZ-API-1042.

Request body: dados enviados. Response body: dados recebidos; JSON organiza campos e valores. Header: informação adicional; Content-Type: application/json indica o formato.

Status HTTP: código que resume a resposta. 200 indica sucesso; 201 indica criação. Neste laboratório, o contrato do POST /api/checkout cria um pedido e exige 201. Nem todo POST exige 201.

Contrato: acordo sobre entrada, status, campos, tipos e regras. Um JSON válido com status de sucesso ainda pode violar esse acordo. A referência aderente é uma resposta didática fixa para comparação; não vem de um serviço independente, não foi executada contra a candidata e não a valida.

E2E acompanha uma jornada integrada. Regressão repete comportamentos conhecidos após mudanças. Aqui você inspeciona contratos de endpoints isolados. Relato de Defeitos ajuda a comunicar os achados obtidos.
